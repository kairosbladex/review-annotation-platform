## 3. 缓存和时间匹配缺陷已复现

当前 `app.py:690`：

```python
@lru_cache(maxsize=16)
def _get_cached_log_poses(log_url):
    return _fetch_log_poses_from_url(log_url)
```

该缓存没有 TTL，键只有 URL。`app.py:704` 中 `OVERLAY_LOG_URL_CACHE` 默认是 `1`，运行容器没有设置关闭它的覆盖值。对于不断追加的飞行日志，同一 URL 的后续请求可能一直使用首次获取的内容，直到条目被淘汰或进程结束。

`app.py:189` 的时间选择逻辑：

```python
abs_secs = [state_t0 + float(p["t_sec"]) for p in poses]
return min(range(len(abs_secs)), key=lambda k: abs(abs_secs[k] - shot_epoch_sec))
```

`app.py:1157` 的请求处理没有在返回所选遥测前检查最大时间差。如果请求时间超出缓存日志的末尾，它会选择最后一条旧记录继续计算。

已在独立 Python 解释器里导入当前部署源码，使用受控日志获取函数模拟同 URL 内容随飞行增长：

1. 首次请求时间为 18:09:02，日志已有最新遥测为 18:09:00。
2. 第二次请求为 18:10:18，源日志已可提供 18:10:18 遥测。
3. 默认缓存路径两次请求只获取一次日志，第二次仍选 18:09:00，旧 **78 秒**，未拒绝。
4. 仅在该独立测试进程里禁用缓存，再次调用后选中 18:10:18，时间差为 0。

**该测试确认了真实代码的失败机制，但日志增长和原始请求参数是测试控制输入，不是从线上 HTTP worker 中恢复出的历史请求或缓存内容。** 没有修改线上缓存、配置或业务数据。

## 5. 图像尺度与前端的剩余范围
