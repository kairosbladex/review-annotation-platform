# 复检微调模型 v2 评测（对比 v1）

## 结论：v2 不能直接替换 v1

v2 更倾向于驳回：减少了一部分误检被放过，但让约 7% 的真车从“自动确认”变成“转人工”。真车变差是统计上确定的，误检减少样本太少、尚不显著。

线上随机流量 200 个框（高清输入，两路一致口径，199 个有效标签）：

| | v1 | v2 |
|---|---|---|
| 自动判对 | 187 | 175 |
| 自动判错（多为误检被放过） | 8 | 5 |
| 转人工 | 4 | 19 |

- 真车 180：v1 自动确认 179，v2 自动确认 167；12 个变差、0 个变好（配对检验 p≈0.0005）。变差的全部变成转人工，没有被错误驳回（两路一致规则要求基础模型也驳回）。
- 非车 19：被放过 7 → 4；3 个变好、0 个变差（p=0.25）。低清输入下 12 → 7（p≈0.06）。
- 楼顶难例 108（高清）：真车自动确认 63 → 54（9 个变差，p≈0.004）；屋顶设施被放过 13 → 8（p≈0.06）。

换算到线上：每 200 个车辆框，大约少放过 3 个误检，同时多 15 个转人工。是否值得是业务取舍；按现有证据不建议上线 v2。

## 检查点选择

v2 训练 3 轮，验证损失 0.035 / 0.069 / 0.077。验证集实际判定（车类 32 个）：第 1 轮判对 29（真车错拒 1），第 2 轮 24（错拒 6），第 3 轮 22（错拒 8）。选第 1 轮 `checkpoint-135`（adapter SHA-256 `5cdbcc75…`）。后续轮次越来越倾向驳回真车，与评测集上的现象一致。

## 可能原因

- 训练脚本按“类别|标签”等权抽样：车类误检 18 个与真目标 92 个被抽到的次数相同，每个误检每轮约被看 1.9 次，真目标只有约 0.4 次，模型被推向“更多驳回”。
- 新增误检来自少数几次飞行任务，场景不够多样，模型可能学到的是“这些场景里的车更可疑”而不是误检本身的特征。
- 验证集车类误检只有 3 个，第 1 轮的“真车错拒 1/29”没能提前暴露问题。

## 方法

- 基础模型不随微调变化，沿用 v1 评测时的基础模型输出；只重跑 v2 adapter，按 (候选, 输入组) 合并后用同一统计脚本（`scripts/merge_adapter_predictions.py`、`scripts/analyze_resolution_ab.py`）。
- 评测集均未进入训练：楼顶难例 108（`data/vehicle-surface-gate-eval-20260929/resolution-ab`）、随机流量 200（`resolution-ab-random`）。v2 解析失败 0。
- 运行：训练用 `ktd-qwen-runtime:clean-source-20260925-v1`，断网，L20 `GPU-c977647c…`；评测用 `yoloe_service_test:vehicle-surface-v3-20260929-v1`，断网，每容器限 7GB 内存、8 核、结束自动删除。经 wxl 授权，部分评测在共享服务 L20 `GPU-9f2ac4d0…` 上运行；看护记录 `gpu_watchdog.log` 显示该卡剩余显存最低 21GB，测试环境复检服务全程 healthy、未重启。
