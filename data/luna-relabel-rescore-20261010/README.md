# Luna 更正标签重算（2026-10-10）

人工复核完成后，用**更正后标签**对三处既有评测重算一遍，并与旧标签结果逐项对比。评分函数直接复用 `luna-prompt-autotune` 的官方 `src/metrics.py`，口径与线上一致：**只有 `true` 放过，`false` 和 `uncertain` 都算驳回**；`uncertain` 单独统计。

## 结论

### 1. 54 框复核只改动了 3 个框，且全部落在 dev

| 复核选项 | 框数 | 对标签的实际影响 |
|---|---:|---|
| 维持原标签 | 49 | 无 |
| 改为是 | 3 | `false` → `true`（**实际更正**） |
| 改为不是 | 1 | 原标签本就是 `false`，与原标签相同，不构成更正 |
| 看不清 | 1 | 不导入，不构成更正 |

`build_correction_list.py` 因此只输出 **3 条**更正，全部是"不是→是"：

| key | 类别 | 原标签 | 更正为 | 所在划分 |
|---|---|---|---|---|
| `released_fp:61b6a8b48d6846b1aca70f777558012d:004` | 车 | false | true | **dev** |
| `released_fp:f7041ee1c1aa4feb952d95667e47b235:001` | 两轮车 | false | true | **dev** |
| `released_fp:61b6a8b48d6846b1aca70f777558012d:005` | 车 | false | true | **dev** |

**这 3 个框全部是 dev，没有一个是 holdout。** 这决定了下面第 2 条结论。

### 2. 三处评测的 holdout 数字完全不变，没有任何 holdout 结论改变

- holdout 两次运行（p000 / p000b）：**新旧逐字段完全一致**。
- p002 holdout 两次运行（a / b）：**新旧完全一致**。
- 违建单卡四轮（holdout 443 框）：**新旧完全一致**。
- 干净图四条件的 holdout 部分（309 框）：**新旧完全一致**。

原因不是"更正没生效"，而是**更正全部落在 dev，而 holdout 的 443 框标签集合与这 3 框不相交**。所以任务里"用更正后标签重算 holdout"这一步是做了的，结果是恒等变换。

### 3. dev 上全部版本一致上移 3 框，排序与门禁不变

7 个版本在 dev 上的正确框数位移全部相同：**+3 框**（各版本 Δacc +0.43~+0.45pp）。因为模型对这 3 个框在所有轮次里都判 `true`，旧标签下它们计为"非目标被放过"，更正后转为答对。

- 排序新旧完全一致：p002 > p005 > p001 > p004 > p003 > p000 > p000b。
- dev 门禁 G1/G2/G3 新旧判定完全相同（G2 仍因光伏板回退不通过、G3 仍因人员误放不通过）。
- 干净图 dev 侧只有车辆的数字变动（准确率 +0.89~+0.90pp、非目标被放过 −2），说法方向不变。

**因此：没有任何一条评测结论因为这次更正而改变。**

| 版本 | 判是精确率 (真裂纹/判是) | 真裂纹召回率 (真裂纹/88) | 非裂纹拒绝率 ((判不是+看不清)/109) |

判断：**不能笼统说 p001 起大量判"不是"是正确的。**

- **对的部分**：对非裂纹的剔除能力大幅提升。非裂纹拒绝率从 p000 的 55.05% 升到 p001~p005 的 84.40%~90.83%；"非目标被放过"从 p000 的 49 个降到 p002 的 10 个；p000/p000b 有 103/78 个框答"看不清"，p001 起降到 5~19 个。
- **错的部分**：真裂纹被大量误驳。真裂纹召回率从 p000 的 48.86% **塌到** p001~p005 的 15.91%~26.14%；"真目标被驳回"从 p000 的 45 个涨到 p001~p005 的 65~74 个；88 个真裂纹里，p001 起直接判"不是"的就有 57~66 个。判"不是"的框里约 **41%~43% 其实是真裂纹**。
- 准确率的小幅提升（48.73%~52.28% → 53.81%~58.38%）几乎全部来自**非裂纹拒绝率**的提升，而不是"判不是"本身更准。判是精确率基本持平（p000 46.74%，p001~p005 45.16%~58.33%），但召回率从 48.86% 掉到 15.91%~26.14%——模型是在整体收缩"判是"（少数派化），而不是学会了认裂纹。
- 需要注意：本口径下"看不清"落在非目标上也算答对，所以所有版本准确率都被抬高了；若只看明确的判是/判不是，p001 起是在"宁可错杀"的方向上走。

## 方法与复现

1. `python3 data/label-adjudication-20261009/build_correction_list.py` → `corrections.csv`（3 条）。
2. `python3 data/road-crack-labeling-20261009/import_labels.py` → `labels-road-crack.json`（该脚本与 `manifest.json` 属 `feature/road-crack-labeling` 分支，本次从该分支取出后在临时目录运行，输出写回本仓库该文件；未改动 `annotations.csv`）。
3. 逐图原始输出：autotune 的 dev 与 holdout 单框结论来自 `raw-runs.tar.gz` 的 `runs/<版本>/out/*.json`；p000b/p002 的 holdout 单框结论取自 `human/final-20261009/*.json` 的 `decisions`；违建四轮取自 `results/*.json` 的 `decisions`；干净图取自 `per-box.json` 的 `decisions`。
4. 评分一律调用官方 `src/metrics.py` 的 `score(results, labels, split)`。
5. 自检：用旧标签重算，逐位复现了原始记录——p000 holdout 0.7562、p000 dev 0.7299、p000b dev 0.7124、p001 dev 0.7608、p000b-holdout 0.7675，以及违建四轮 0.7607/0.7585/0.7991/0.8149。
6. 新标签 = 旧标签基础上把上述 3 个 key 的 `label` 由 `false` 改为 `true`，其余 1125 框不动。

## 限制与未决

- 这次复核只覆盖了按规则挑出的 54 框（"疑似误标"队列），不是全部 1128 框。49/54 维持原标签说明该队列的误报率很高，但**未抽到的框仍可能标错**，本报告没有也无法排除。
- 更正全部落在 dev，所以 holdout 的绝对水平仍建立在**未经复核的 443 框标签**上。holdout 结论的可靠性没有得到这次复核的任何加强。
- 道路裂纹的 197 框金标来自单人标注，没有做类似的复核；"p001 起误驳率高"这一判断受该单人标签质量影响。
- 道路裂纹的"大量判不是"只在一个 197 框的无标签池上观察到，样本小且类别单一，不足以推广到其他类别。
- 本次**未调用任何模型**，全部结论来自既有原始输出的重新计分。
